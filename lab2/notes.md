## Part 2 – Using xv6

Commands I ran at the `$` prompt: `ls`, `cat README`, `echo hello xv6`, `ls | grep c`, `wc README`.

```
$ echo hello xv6
hello xv6
$ ls | grep c
cat            2 3 36728
echo           2 4 35592
wc             2 17 37728
sync           2 22 34944
console        3 25 0
$ wc README
48 336 2441 README
```

(`ls` columns are: name, type (1 = directory, 2 = file, 3 = device), inode number, size in bytes.)

**(1) Three programs xv6 ships with:**
`ls`, `cat` and `echo` (`ls` also listed `grep`, `wc`, `sh`, `kill`, `mkdir`, `rm`, `ln`, `usertests`, and so on). After my changes the list also has my own `sleep` and `pingpong`.

**(2) Which two OS features must exist for a pipe to work?**
1. **Processes, with `fork()`**: the shell has to create two separate processes, one for `ls` and one for `grep`, running at the same time (`user/sh.c:105` and `user/sh.c:112` call `fork1()`; in the kernel this is `kfork()` in `kernel/proc.c:259`).
2. **Inter-process communication, i.e. the `pipe()` system call plus file descriptors**: the kernel makes a buffer with a write end and a read end (`sys_pipe` in `kernel/sysfile.c:502`, `pipealloc` in `kernel/pipe.c:23`). The shell uses `close()` + `dup()` so that `ls`'s stdout (fd 1) goes into the pipe and `grep`'s stdin (fd 0) comes out of it (`user/sh.c:101-123`). `pipewrite` / `piperead` (`kernel/pipe.c:77`, `:112`) move the bytes and make the reader sleep until data arrives.

**(3) xv6 shell vs. Linux shell (one sentence):**
It feels the same for the basics (commands, arguments, `|`, `>`, `<`, `&`, `;`), but it is much smaller: no tab completion, no history, no variables or `$PATH` (`exec` at `user/sh.c:79` just uses the name as given), no scripting, and `ls` prints raw inode numbers and sizes instead of `rwx` permissions and owners.

## Part 3 – Reading the source

```
$ grep -n "sys_read\|sys_write" kernel/sysfile.c | head
69:sys_read(void)
83:sys_write(void)
```

**(1) Which system calls does `user/cat.c` use, and what does each one ask the kernel?**

| system call | where in `user/cat.c` | what it asks the kernel |
|---|---|---|
| `open(path, O_RDONLY)` | line 35 | "find this file and give me a file descriptor for reading" |
| `read(fd, buf, 512)` | line 12 | "copy up to 512 bytes from this file into my buffer" (returns 0 at end of file) |
| `write(1, buf, n)` | line 13 | "send these n bytes to fd 1", i.e. standard output / the console |
| `close(fd)` | line 40 | "I am done with this file, free the descriptor" |
| `exit(0 / 1)` | lines 15, 20, 31, 37, 42 | "end my process and return this status to the parent" |

`fprintf(2, ...)` (lines 14, 19, 36) is not a system call itself. It is a library function in `user/printf.c` that ends up calling `write` on fd 2 (stderr).
The calls are declared in `user/user.h` (`read` line 11, `write` line 10). The stubs are generated by `user/usys.pl` (`entry("read")` line 28): each stub puts the call number in register `a7` (`SYS_read` = 5, `kernel/syscall.h:6`) and runs the `ecall` instruction, which jumps into the kernel.

**(2) In which kernel file and line is `sys_read` implemented?**
In **`kernel/sysfile.c`, line 69** (the return type `uint64` is on line 68, and the function body runs to line 80). It reads the three arguments (`argaddr`, `argint`, `argfd`) and calls `fileread()` (`kernel/file.c:107`). `sys_write` is right below it, on line 83.
Path of one `read()`: `ecall` → `usertrap()` (`kernel/trap.c:38`, calls `syscall()` on line 68) → `syscall()` (`kernel/syscall.c:137`) looks up `syscalls[a7]` → `[SYS_read] = sys_read` (`kernel/syscall.c:115`) → `sys_read()`.

**(3) Difference between `kernel/` and `user/` (one sentence):**
`kernel/` is the OS itself: it runs in privileged supervisor mode and can touch the hardware, all memory and every process. `user/` programs run in unprivileged user mode, each in its own memory, and can only get things done by asking the kernel through system calls.

## Part 4 – my program `sleep` (and the `pause()` rename)

The lab sheet uses `sleep(atoi(argv[1]))`, but that **does not compile on current xv6**. In commit **f5dea58** (Robert Morris, 19 Aug 2025, "user sleep() -> pause() … SYS_sleep -> SYS_pause") the user-level system call was renamed to `pause()`, because the kernel uses `sleep()` for its internal sleep/wakeup. Now `user/user.h:25` declares `int pause(int);`, it is `SYS_pause` = 13 (`kernel/syscall.h:14`), and the kernel handler is `sys_pause()` in `kernel/sysproc.c:68`. So `user/sleep.c` calls `pause()` (a comment in the file explains this).

`sys_pause` waits in a loop until `ticks - ticks0 >= n`. `ticks` is increased in `clockintr()` (`kernel/trap.c:167/171`), and the timer is set to `r_time() + 1000000`, "about a tenth of a second" (`kernel/trap.c:177-179`). So one tick ≈ 0.1 s.

Tests (real output, and time measured by the script):

```
$ sleep 10              # (script timer: back to prompt after 1.19 s)
$ sleep
usage: sleep <ticks>
$ sleep 50              # (script timer: back to prompt after 5.41 s)
$ pingpong
14: received ping
13: received pong
```

The timings match about 0.1 s per tick. In `pingpong`, the child (pid 14) got the byte from the parent over the first pipe and printed "received ping". Then the parent (pid 13) got it back over the second pipe and printed "received pong".
